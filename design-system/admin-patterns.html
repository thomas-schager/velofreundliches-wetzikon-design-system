Admin-Backend UI-Patterns

Das Admin-Backend hat ein eigenes Komponenten-Set (.adm-*, in velofreundliches-wetzikon-backend/app/public/assets/admin.css) — bewusst getrennt von der öffentlichen Seite (.vw-*), wie in design-system-sharing-strategy.md entschieden: eine Login-Maske, ein Datentabellen-Backend und eine Moderations-Queue bilden sich nicht sinnvoll auf ein Marketing-Seiten-Komponenten-System ab. Was weiterhin geteilt wird, sind die Design Tokens (Farben, Abstände, Radien, Schatten) — jedes Pattern hier ist damit gebaut, nicht mit eigenen Werten.

Diese Seite dokumentiert nicht jede CSS-Klasse aus admin.css, sondern die Interaktionsmuster, die mehrfach unabhängig wiederverwendet wurden (oder klar dafür bestimmt sind) — mit der Regel dahinter, nicht nur dem Aussehen. Feature-spezifisches Markup (z.B. der Routen-Editor: Typ-Pillen, Legende, Wegpunkt-Marker) gehört nicht hierher, weil keine andere Backend-Seite es wiederverwenden würde.

Grundlage .adm-btn
Buttons

Fünf Varianten, eine Bedeutung pro Kontext: primary für die eine Haupthandlung einer Ansicht, secondary für gleichrangige/neutrale Aktionen, danger für zerstörerische, ghost für die unauffälligste Stufe (z.B. "Abbrechen" in einer Symbolleiste). Nie zwei --primary-Buttons nebeneinander — das ist der häufigste Fehler, der die Hierarchie zerstört.

Deaktivierter Zustand: opacity: 0.45 + cursor: not-allowed — immer mit einem title-Attribut, das erklärt warum (siehe Sticky Action Bar unten für die Regel, wann überhaupt deaktiviert wird).

Interaktionsmuster .adm-sticky-actions
Sticky Action Bar

Fixierte Fussleiste für die Haupthandlungen einer Bearbeitungsansicht — bleibt beim Scrollen erreichbar, unabhängig von der Seitenlänge. Statustext links (margin-right: auto schiebt die Buttons nach rechts), Aktionen rechts, sekundär vor primär.

Regel: nur deaktivieren, wenn die Aktion aktuell wirkungslos wäre.

Nicht "immer aktiv" und nicht "grundsätzlich deaktiviert bis geprüft" — sondern präzise: ein Button ist deaktiviert genau dann, wenn ein Klick gerade nichts Sinnvolles täte. Ein reiner Speichern/Verwerfen-Button ist wirkungslos, solange nichts geändert wurde. Ein Workflow-Button wie "Veröffentlichen" ist wirkungslos, wenn der Datensatz das Ziel bereits erreicht hat — unabhängig davon, ob gerade ein Feld bearbeitet wurde. Beide Fälle sind unten als Live-Beispiel zu sehen, weil sie in der echten Anwendung unterschiedliche Regeln brauchen, nicht dieselbe Logik kopiert bekommen.

2× verwendetVariante: Speichern/Verwerfen
Keine ungespeicherten Änderungen

Routen-Editor (/routen): reine "ungespeicherte Änderungen"-Leiste, keine Workflow-Bedeutung. Beide Buttons deaktiviert, bis der Status wirklich "dirty" ist — und zusätzlich, solange eine einzelne Routen-Aktion (Zeichnen/Wegpunkte/Löschen) noch offen ist, weil "den ganzen Änderungssatz speichern" während einer einzelnen unfertigen Aktion keine wohldefinierte Bedeutung hätte.

2× verwendetVariante: Workflow (drei Buttons)
Status: Veröffentlicht

Meldungs-Prüfung: "Änderungen speichern" folgt derselben Dirty-Regel wie oben; "Veröffentlichen"/"Ablehnen" sind Workflow-Übergänge und daher unabhängig von Feldänderungen — nur deaktiviert, wenn der Datensatz den jeweiligen Zielstatus bereits hat (hier: bereits veröffentlicht, "Ablehnen" bleibt möglich).

CSS
.adm-sticky-actions {
  position: sticky; bottom: 0; margin-top: var(--space-6);
  background: #fff; border: 1px solid var(--color-border); border-radius: var(--radius-md);
  padding: 14px 18px; display: flex; align-items: center; gap: 10px; flex-wrap: wrap;
  box-shadow: var(--shadow-lg);
}
.adm-sticky-actions__status { font-size: 13px; color: var(--color-text-muted); margin-right: auto; }

Statustext trägt aria-live="polite", damit ein Statuswechsel (z.B. "Ungespeicherte Änderungen") auch ohne Fokus auf der Leiste per Screenreader angekündigt wird.

Interaktionsmuster rotate 180deg
Ausklapp-Muster (Chevron)

Ein Trigger, ein rotierendes Chevron-Icon, ein Inhalt, der bei Bedarf erscheint. Unabhängig dreimal im Backend entstanden — Nutzermenü, Sidebar-Einklappen, Versionsverlauf-Zeilen — bevor es hier als ein Muster benannt wurde. Genau dieser Umstand (mehrfach unabhängig erreicht, nicht einmal erfunden und überall hinkopiert) ist, warum es dokumentiert wird: die nächste Stelle, die "etwas ausklappbar machen" braucht, soll dieses Muster wiederverwenden statt ein viertes zu erfinden.

3× verwendetlive
Details erscheinen erst, wenn die Zeile geöffnet wird — nicht permanent sichtbar, um die Liste kompakt zu halten.

Klick zum Testen. Kollabiert startet immer eingeklappt (nie standardmässig offen); der Zustand liegt in einer .is-open-Klasse auf dem äusseren Element, nicht auf dem Trigger selbst, damit Trigger und Inhalt vom selben Zustand gesteuert werden.

CSS
.x-trigger { display: flex; align-items: center; justify-content: space-between; cursor: pointer; }
.x-chevron { transition: transform var(--dur) var(--ease); }
.x.is-open .x-chevron { transform: rotate(180deg); }
.x-body { display: none; }
.x.is-open .x-body { display: block; }
trigger.addEventListener('click', function () {
  var expanded = container.classList.toggle('is-open');
  trigger.setAttribute('aria-expanded', expanded ? 'true' : 'false');
});

aria-expanded auf dem Trigger-Button gehört immer dazu, nicht nur die visuelle Rotation.

Interaktionsmuster .adm-modal
Bestätigungs-Modal

Für eine Aktion, die eine Zusammenfassung braucht, bevor sie unumkehrbar wird (z.B. der Routen-Editor zeigt vor jedem Speichern eine Änderungsliste). Kein generisches "Bist du sicher?" — der Modal-Inhalt zeigt konkret, was passiert, damit die Bestätigung eine informierte Entscheidung ist, keine Formsache.

Änderungen bestätigen

2 hinzugefügt · 1 entfernt · 0 geändert

Konkrete, prüfbare Zusammenfassung statt generischer Warnung — z.B. eine Liste betroffener Objekte.

Overlay rgba(0,0,0,0.5), Modal selbst var(--shadow-lg) + var(--radius-lg), max-width 560px. "Abbrechen" immer secondary/links, die bestätigende Aktion immer primary/rechts — Klickreihenfolge von links (Rückzug) nach rechts (Commit), nie umgekehrt.

Interaktionsmuster .adm-toast
Toast

Kurze, sich selbst schliessende Bestätigung nach einer bereits abgeschlossenen Aktion ("Änderungen gespeichert.") — kein Blocking-Dialog, keine Handlung erforderlich. Unten mittig, 2.5 Sekunden sichtbar. Nicht für Fehler verwenden, die eine Reaktion brauchen (dafür .adm-alert--error oder alert(), je nach Dringlichkeit) — ein Toast verschwindet von selbst, eine Fehlermeldung, die jemand vielleicht gerade nicht sieht, darf das nicht tun.

Änderungen gespeichert.
Statusanzeige .adm-alert
Alerts

Inline-Hinweis innerhalb einer Seite (nicht schwebend wie Toast, nicht blockierend wie Modal) — info/success/error, jeweils mit eigenem Tint statt reinem Rot/Grün, damit es neben den Bewertungsfarben (--color-rate-*) nicht zu Verwechslungen kommt.

Dev-Modus: Code wird zusätzlich hier angezeigt.
Passwort erfolgreich geändert.
E-Mail-Adresse oder Passwort ist falsch.
Statusanzeige .adm-badge
Badges

Kompakter Statusindikator für Listen/Detail-Header — Farbe kodiert Bedeutung konsistent mit den Alert-Tints oben, nicht neu erfunden pro Status.

Neu Veröffentlicht Abgelehnt
Statusanzeige .adm-empty
Empty State

Für jede Liste/Tabelle, die leer sein kann — Icon, kurzer Titel, ein erklärender Satz. Kein einfaches "Keine Daten"; die Erklärung sagt, warum die Liste leer ist oder was als Nächstes passiert (z.B. Versionsverlauf: "die erste wird beim nächsten Speichern angelegt").

Keine Meldungen

Neue VeloMelder-Einreichungen erscheinen hier automatisch.

Referenz Quelle
Wo verwendet

Diese Seite ist Referenz-Dokumentation, keine Kopie der echten Stylesheets — die tatsächlichen .adm-*-Klassen leben ausschliesslich im Backend-Repo (Tokens, nicht Komponenten, werden zwischen den Repos geteilt, siehe design-system-sharing-strategy.md). Bei Widerspruch zwischen dieser Seite und dem echten CSS gilt das CSS als Quelle der Wahrheit — diese Seite dann nachziehen.

  • velofreundliches-wetzikon-backend · app/public/assets/admin.css — Quelle aller Werte auf dieser Seite (Abschnitte BUTTONS, MELDUNG DETAIL, ROUTE EDITOR).
  • velofreundliches-wetzikon-backend · app/templates/admin/routes.html.twig + routes-editor.js — Sticky Action Bar (Variante Speichern/Verwerfen), Ausklapp-Muster (Versionsverlauf), Bestätigungs-Modal, Toast.
  • velofreundliches-wetzikon-backend · app/templates/admin/meldung_detail.html.twig — Sticky Action Bar (Workflow-Variante), Alerts, Badges.
  • velofreundliches-wetzikon-backend · app/templates/admin/_layout.html.twig — Ausklapp-Muster (Nutzermenü, Sidebar-Einklappen).
  • velofreundliches-wetzikon-backend · app/templates/admin/meldungen.html.twig — Empty State, Badges.
